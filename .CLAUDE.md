# Repo rules — LDE-useful-agent-skill-rules

A flat library of general-use agent skills and rules. **This repo deliberately
does not follow the standard agent-skill directory format** (`<skill>/SKILL.md`
plus `scripts/`, `references/`, `assets/`). Do not restructure it into that
layout, and do not create a `SKILLS/` directory.

## Layout

```
./                              repo root — one .md file per skill
  .CLAUDE.md                    this file
  README.md
  shell-source-encapsulation.md a skill
  <skill-name>.md               a skill
  _tests_/
    <skill-name>/               test scripts for that skill only
      run-tests.sh
```

## Rule 1 — one skill, one file

Every skill is a **single self-contained `.md` file at the repo root**, named
`<skill-name>.md` in kebab-case. No per-skill directory. No `SKILL.md`. No
sidecar files.

## Rule 2 — standalone is non-negotiable

A skill file must be complete on its own. Someone who copies that one file into
another repo, or reads it with no access to anything else here, gets the whole
skill.

That means **inline everything the skill needs**: templates, snippets, config
examples, checklists, tables. Nothing a reader has to follow to be able to do
the work may live in another file. If a skill wants to hand over a template
file, the template's full text is a fenced code block inside the skill.

Corollary: a skill must not `Read`, `source`, or otherwise depend on
`_tests_/` at runtime. Referencing a test script as an *optional* convenience
("a runnable checker lives at `_tests_/<skill>/x.sh`") is fine only when the
skill already contains an inline way to do the same job.

## Rule 3 — tests live in `_tests_/<skillName>/`

Any script for a skill — verifiers, fixtures, behavior probes, examples that get
executed — goes in `_tests_/<skill-name>/`. The directory name matches the skill
file's basename exactly.

- Scripts are executable (`chmod +x`) and runnable from any working directory.
- Exit `0` on pass, non-zero on failure; print what failed.
- Tests should re-verify the factual claims the skill makes, so a shell/tool
  upgrade that invalidates the skill shows up as a test failure.
- Tests may extract code blocks out of the skill file to test them — that keeps
  Rule 2 honest by proving the inlined copy is the one that works.

## Rule 4 — frontmatter

Every skill file opens with YAML frontmatter carrying exactly `name` and
`description`:

```markdown
---
name: shell-source-encapsulation
description: One line on what it does, then "Use when …" covering the phrasings, symptoms and file types that should trigger it.
---
```

`name` is kebab-case and **identical** to the filename without `.md` and to the
`_tests_/` directory name. `description` is written for retrieval: state the
job, then the trigger conditions — the words a user would actually type, the
error messages, the file kinds involved. It is the only thing an agent sees when
deciding whether to open the file.

## Rule 5 — claims must be verified

These skills are instructions an agent will follow without checking. So:

- Run the commands before documenting their behavior. Record what actually
  happened, not what the manual implies.
- Say which versions/platforms a behavior was verified on when it varies
  (bash vs zsh, macOS vs GNU coreutils).
- Prefer a table of verified inputs → outcomes over prose assurances.
- No aspirational instructions. If it wasn't run, don't state it as fact —
  mark it explicitly as untested.

## Rule 6 — shape of a skill file

Keep them scannable and imperative:

1. `#` title — the rule or job, stated as an outcome.
2. The rule/statement up front, in a blockquote or short section. Reader should
   know what they must do within the first screen.
3. Why it is true / what breaks without it — brief, mechanism-level.
4. The method(s), with copy-ready code.
5. A checklist an agent can walk.
6. A gotcha/symptom → cause → fix table.

Second person, imperative. No preamble, no "in this document we will".

## Adding a skill

- [ ] `./<skill-name>.md` at the root, frontmatter `name` == filename basename.
- [ ] Fully self-contained — templates and examples inlined.
- [ ] Every factual claim executed and verified first.
- [ ] Tests in `_tests_/<skill-name>/`, executable, non-zero on failure.
- [ ] One line added to `README.md` pointing at it.

## Note

Claude Code auto-loads `CLAUDE.md`, not `.CLAUDE.md`, so this file is a
convention document read on request rather than injected into every session.
Rename it or add a `CLAUDE.md` symlink if you want it loaded automatically.
